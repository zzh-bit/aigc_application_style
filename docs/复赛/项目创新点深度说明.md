## 一、问题洞察与设计哲学

### 1.1 核心洞察

**重大决策时，人的内心天然存在多个声音。**

- 一个说"冲一把"——追求成长和突破
- 一个说"稳一点"——害怕失去和风险
- 一个问"十年后回头看呢？"——关注长期和意义

但在现实中，这些声音**在脑中混战**——缺乏结构化表达、对比和记录。用户往往：

- 被最响亮的那个声音主导（通常是恐惧或冲动）
- 无法同时权衡多个维度（收益、风险、情绪、长期影响）
- 决策后无法复盘——"我当时到底是怎么想的？"

### 1.2 现有方案的三大鸿沟

| 鸿沟 | 现状 | 后果 |
|------|------|------|
| **视角鸿沟** | AI 问答工具只提供单一视角建议 | 无法模拟内心多维度博弈 |
| **记忆鸿沟** | AI 不了解"你"——每次对话从零开始 | 建议泛化、不个性化，无法形成成长飞轮 |
| **闭环鸿沟** | 决策辅助工具止步于"给建议" | 无法追踪、验证、复盘、成长 |

### 1.3 PS² 的设计哲学

> **"不替你决策，帮你看清自己"**

- **多视角而非单一答案**：你的内心有多个声音，我们让它们有序辩论
- **AI 了解你而非替代你**：基于记忆的个性化，但最终判断永远在你手中
- **闭环而非一次性**：辩论 → 推演 → 归档 → 洞察 → 验证，形成成长飞轮
- **隐私优先**：数据在本地，AI 是工具而非窥探者

## 创新 1：多 Agent 人格辩论架构

### 1.1 核心概念

**不是"问 AI → 得一个答案"，而是"让你的多个内心声音有序辩论，你来旁听判断"。**

将心理学中的**内在家庭系统（IFS）理论**工程化：人内心存在多个"子人格"（激进者、保守者、未来观察者），PS² 用 AI Agent 分别扮演这些子人格，展开结构化辩论。

### 1.2 解决的关键问题

| 传统 AI 问答的局限 | PS² 的解决方案 |
|-------------------|---------------|
| 单一视角回复，忽略内心矛盾 | 三方视角并行生成，保留分歧而非强行统一 |
| 无个性化，不知道"你是谁" | 记忆 RAG 检索注入，角色引用你的过往经历 |
| 一问一答，被动响应 | 多轮追问、可引导辩论方向、可选导入导师 |
| AI 替你决策 | 呈现分歧，由你判断——保持决策自主性 |

### 1.4 Prompt 工程深度

每个 Agent 的 System Prompt 包含四个层次：

| 层次 | 激进派 | 保守派 | 未来派 |
|------|--------|--------|--------|
| **核心价值观** | 突破、成长、冒险 | 稳定、安全、渐进 | 长期、趋势、可能性 |
| **思维模型** | 机会导向、损失厌恶低 | 风险导向、损失厌恶高 | 10年尺度、二阶效应 |
| **语气风格** | 热血、直接、行动派 | 谨慎、稳健、重证据 | 冷静、宏观、哲学感 |
| **输出约束** | ≤3句、口语化、不评判用户 | ≤3句、口语化、不恐吓用户 | ≤3句、口语化、不说教 |

### 1.5 角色一致性维护

通过 `inferFactionLearning()` 分析各派系的历史发言倾向，在后续多轮辩论中维持角色人设一致性：

- 激进派始终倾向"行动"和"变化"
- 保守派始终倾向"稳定"和"风险考量"
- 未来派始终关注"长期影响"和"趋势判断"

## 创新 2：Grounded-First 决策推演引擎 ★ 核心技术

### 2.1 核心概念

**这是 PS² 最核心的技术创新**——把抽象的人生决策变成**可对比、可量化、可复盘**的可视化路径图。

**"Grounded-First"的含义**：路径的**结构**（有几条路、叫什么名、谁和谁互斥）由确定性规则解析——这是"Grounded"；路径的**语义**（路上有什么风景、风险多大、能收获什么）由 LLM 丰富——这是"Semantic Enrichment"。

### 2.2 纯 LLM 推演的三大致命缺陷

如果直接让 LLM 自由生成决策推演：

| 缺陷 | 表现 | 根本原因 |
|------|------|---------|
| **分支数不可控** | 同一议题有时生成2条路径，有时5条 | LLM是概率模型，不是逻辑引擎 |
| **路径名不稳定** | "去北京"有时叫"北漂路线"，有时叫"一线城市方案" | LLM创造性命名不可复现 |
| **结果不可复现** | 同一议题推演两次，得到完全不同路径 | temperature > 0 必有随机性 |

**本质问题**：用概率模型做需要确定性的决策辅助，架构本身就错了。

### 2.4 议题类型识别算法

`extractDecisionOptionsFromTopic()` 支持多种中文自然语言句式：

| 句式类型 | 正则/规则 | 示例 | 生成路径数 |
|---------|----------|------|-----------|
| 二元决策 | `要不要…` `该不该…` `是否…` | "要不要去北京工作？" | 2（做/不做） |
| 对称选择 | `A还是B` `A或B` | "考研还是直接工作？" | 2（A/B） |
| 多城市列表 | 城市名+动词 | "北京、上海、深圳选哪个？" | N（按城市数） |
| 多方向展开 | `…还是…还是…` | "考研、就业、创业怎么办？" | N（按方向数） |
| 英文句式 | `Should I...` `A or B` | "Should I quit my job?" | 2 |
| 模糊议题 | 无明确结构 | "对未来很迷茫" | 2-4（提取关键词） |

### 2.5 领域感知（Domain Awareness）

`detectDomainKind()` 识别议题所属领域，为不同领域选用不同的分析维度和富模板：

| 领域 | 关键词 | 专属分析维度 |
|------|--------|-------------|
| 职业发展 | 工作/跳槽/辞职/offer/转行 | 薪资成长、行业前景、技能积累、人脉 |
| 搬迁移居 | 搬家/城市/北京/上海/深圳 | 生活成本、社交网络、气候适应、机会密度 |
| 亲密关系 | 恋爱/分手/结婚/表白/对象 | 情感投入、长期匹配、沟通成本、价值观 |
| 学业教育 | 考研/留学/专业/学校/读博 | 投入产出比、兴趣匹配、就业前景、时间成本 |
| 财务投资 | 买房/投资/股票/理财/创业 | 风险收益比、流动性、时间周期、机会成本 |
| 家庭关系 | 父母/家人/回老家/孝顺 | 代际责任、个人自由、沟通策略、时间分配 |
| 通用 | 不匹配上述 | 收益/风险/情绪/长期影响（四维通用模板） |

```
│   🔮 未来派（支持度 70%）  │  │   🔮 未来派（支持度 55%）  │
│   "10年后的你不会后悔      │  │   "不是非此即彼，也许      │
│   尝试，但会后悔没试…"     │  │   可以先远程兼职试水…"     │
└──────────────────────────┘  └──────────────────────────┘
```

**核心设计理念**：不是"AI 告诉你怎么选"，而是把选择变成**可对比的数据**——收益、风险、情绪、多方意见——你来做最终判断。

### 2.7 质量保障机制

| 机制 | 实现 | 作用 |
|------|------|------|
| **分支名校验** | `isValidBranchName(name, topic)` | 拒绝LLM生成的跑题/垃圾name |
| **折中路径过滤** | `filterGenericBlendPaths()` | 拒绝"折中/妥协"第三条假路径 |
| **跑题检测** | `projectionBranchesLookOffTopic()` | 检测LLM输出是否偏离原议题 |
| **低分回退** | LLM输出质量评分 | 低质量时自动回退本地领域富模板 |
| **本地兜底** | `buildGroundedProjectionFromCouncil()` | LLM完全不可用时仍可离线推演 |
| **自动验证** | `scripts/verify-projection-topics.ts` | 18条测试议题矩阵自动回归 |

### 2.8 对比传统方案

| 方案 | 路径确定性 | 内容质量 | 可复现性 | 领域适配 |
|------|----------|---------|---------|---------|
| 纯LLM自由生成 | ❌ 不稳定 | ⚠️ 可能跑题 | ❌ 不可复现 | ❌ 依赖prompt |
| 固定问卷模板 | ✅ 完全确定 | ❌ 模板化 | ✅ | ❌ 无感知 |
| 混合方案(LLM+后对齐) | ⚠️ 需要事后修正 | ✅ | ⚠️ 依赖LLM质量 | ⚠️ |
| **Grounded-First** | ✅ 规则保证 | ✅ LLM丰富 | ✅ 骨架确定 | ✅ 领域感知 |

## 创新 3：个人记忆 RAG 检索增强

### 3.1 核心概念

**让 AI 了解"你"——基于你的历史记忆进行个性化回复，越用越懂你。**

传统 AI 的"失忆症"：每次对话都从零开始。不管你之前告诉过 AI 多少次"我性格偏保守""我上次冲动跳槽后悔了""我妈妈身体不好我想多陪她"——下次打开对话，它全忘了。

PS² 的记忆 RAG 系统解决了这个问题：AI 在议会辩论和导师对话时，自动检索你的相关记忆并注入上下文，让建议真正"懂你"。

### 3.2 技术架构

```
┌─────────────────────────────────────────────────────────────┐
│                      记忆生命周期                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① 创建记忆                                                  │
│     用户输入标题+正文                                         │
│           ↓                                                 │
│     本地存储到 IndexedDB（隐私优先，数据不出设备）              │
│           ↓                                                 │
│     异步调用 /api/summarize → DeepSeek 生成摘要+关键词         │
│           ↓                                                 │
│     更新 IndexedDB 记录，状态: "summarized"                  │
│                                                             │
│  ② 检索记忆（议会辩论/导师对话时触发）                         │
│     selectRelevantMemories(topic, messages, allMemories)     │
│           ↓                                                 │
│     多维评分检索：                                            │
│     ├─ 标题关键词匹配（权重 2.0）                             │
│     ├─ 正文分句匹配（权重 1.5）                               │
│     ├─ 整体关键词重叠（Jaccard相似度）                        │
│     ├─ 二元组重叠（bigram overlap）                           │
│     ├─ 年份匹配（同一年记忆加权）                             │
│     └─ 去重过滤（bestScore * 0.22 相对阈值）                 │
│           ↓                                                 │
│     Top-K 相关记忆 → 注入 prompt                             │
│                                                             │
│  ③ 记忆引用                                                  │
│     AI回复中包含引用记忆的标签，用户可感知"AI为什么这样说"      │
│                                                             │
│  ④ 记忆管理                                                  │
│     搜索/筛选/时间线浏览/编辑/删除/导出全部                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 检索算法核心

`lib/memory-context.ts` 中的 `selectRelevantMemories()`：

```
输入：当前议题 + 对话历史 + 全部记忆数组
输出：Top-K 条最相关记忆（含相关性评分）

评分维度：
1. 字面匹配分：议题中的词是否出现在记忆标题/正文的句子中
2. 二元组分：议题和记忆的字符二元组重叠比例
3. 关键词分：AI生成的关键词与议题的重叠
4. 时序加权：同年记忆加权 1.2x

过滤策略：
- 相对阈值：保留评分 ≥ maxScore × 0.22 的记忆
- 上限控制：最多返回 5 条（防止prompt过长）
- 去重：按记忆ID去重
```

### 3.4 隐私设计（核心差异化）

| 设计决策 | 实现 | 理由 |
|---------|------|------|
| **本地优先** | 所有记忆存储在 IndexedDB，不自动上传 | 记忆是私密数据，用户拥有完全控制权 |
| **临时注入** | LLM调用时才将片段传入prompt，处理后不存 | 服务端不留存用户记忆 |
| **可控导出** | 支持一键导出/清空全部数据 | 数据可迁移性 |
| **离线可用** | APK模式下记忆功能完全本地运行 | 网络断开不影响核心体验 |

### 3.5 用户场景示例

```

系统检索到相关记忆：
```

## 创新 4：跨时间自我对话系统（未来信件）

### 4.1 核心概念

**不是普通的"定时发送消息"，而是基于 AI 感知的智能触发 + 双向对话 + 议会批注的时空通信系统。**

让用户可以与"过去/未来的自己"建立持续对话——写信时记录预测，收信时对比现实，可视化自我认知偏差。

### 4.2 三重智能触发机制

这是未来信件系统最核心的创新——不同于传统"时间胶囊"只能按日期触发：

| 触发类型 | 原理 | 技术实现 | 使用场景示例 |
|---------|------|---------|------------|
| **📅 日期触发** | 指定送达日期，到期自动进入收件箱 | 客户端定时检查 `deliverAt` | "2027年生日收到这封信" |
| **💭 情绪触发** | AI实时检测用户文本情绪，与信件预设情绪匹配时自动送达 | `triggerLettersByChatKeywords()` 检测12种情绪关键词 | 写"焦虑时打开"→ 检测到焦虑→ 触发 |
| **🎯 事件触发** | 绑定人生节点关键词（面试/考试/生日等） | 检测7种人生事件关键词 | "面试前一天收到鼓励信" |

### 4.3 情绪触发引擎

`lib/letter-trigger.ts` 中的 `triggerLettersByChatKeywords()`：

**12种预设情绪**，每种有对应关键词列表：

```
焦虑：焦虑、不安、担心、紧张、慌…
迷茫：迷茫、不知道怎么办、困惑、迷失…
疲惫：累、疲惫、筋疲力尽、撑不住…
孤独：孤独、寂寞、没人理解、一个人…
低落：低落、难过、伤心、哭…
压力：压力、喘不过气、受不了、崩溃…
平静：平静、安心、放松、踏实…
开心：开心、高兴、快乐、幸福…
兴奋：兴奋、激动、期待、迫不及待…
感恩：感恩、感谢、谢谢、幸运…
自信：自信、相信、一定、没问题…
```

**7种人生事件**：决策、面试、考试、生日、纪念日、新年、成就/失败

**否定检测**：防止"我不焦虑"误触发——匹配否定词前缀。

### 4.4 时空对话线程

```
时间轴 ──────────────────────────────────────────────────────→

2025年3月                    2025年9月                 2026年3月
    │                            │                         │
    │ 写信给"半年后的自己"        │ 收到信！                │
    │ "你现在还焦虑吗？"          │ 回信给"半年前的自己"    │
    │ 预测：会找到方向            │ "确实还在焦虑，但..."    │
    │ threadId: "th_001"         │ threadId: "th_001"     │
    │                            │                         │
    └──────── 同一线程 ──────────┘                         │
                                                            │
                                          再次收到回信（循环）
                                          threadId: "th_001"
```

**核心特性**：
- `threadId` 关联形成持续跨时间对话
- "过去自己 ↔ 未来自己"双向通信，非单向留言
- 每次回信扩展同一线程，构建跨时间成长轨迹

### 4.5 议会批注加持

信件送达时不是冷冰冰的通知，而是附带三派系角色的"智慧解读"：


### 4.6 预测 vs 现实

写信时记录预测 → 收信时与实际对比 → 可视化自我认知偏差：

```
偏差分析：
┌────────────────────────────────────────┐

│  过去3次预测中，2次实际比预测慢了       │
│  40%以上。建议下次做计划时乘以1.5倍。   │
└────────────────────────────────────────┘
```

这是心理学中"预测偏差（Forecasting Bias）"概念的实用化工具。

## 创新 6：导师智库——八大思想家对话系统

### 6.1 核心概念

**8 位跨越 2500 年的人类思想大师，以各自独特的思维模型和表达风格与你进行 1:1 深度对话。**

每位导师不是简单"模仿语气"，而是**内化其思维模型**——苏格拉底不会直接给你答案，他用追问让你自己找到答案；荣格不会分析表面行为，他关注你没有说出口的潜意识。

### 6.2 八位导师的思维模型

| 导师 | 时代 | 核心思维模型 | 对话风格 | 擅长领域 |
|------|------|------------|---------|---------|
| **苏格拉底** | 古希腊 | 定义追问法：连续追问直到发现矛盾 | 反问为主，不预设答案 | 澄清困惑、定义问题 |
| **马可·奥勒留** | 古罗马 | 可控圈二分法：区分能控/不能控 | 平静理性，聚焦当下行动 | 焦虑管理、接纳现实 |
| **卡尔·荣格** | 20世纪 | 潜意识分析：阴影整合、自性化 | 深沉洞察，关注没说出口的 | 自我认知、内心冲突 |
| **丹尼尔·卡尼曼** | 当代 | 系统1/2：快思考vs慢思考 | 理性分析，拆解认知偏误 | 决策分析、风险评估 |
| **老子** | 春秋 | 无为辩证：反者道之动 | 简短深邃，言有尽意无穷 | 放下执念、顺势而为 |
| **孙子** | 春秋 | 知己知彼：形势评估框架 | 策略清晰，重视信息优势 | 竞争策略、资源评估 |
| **孔子** | 春秋 | 仁礼忠恕：推己及人 | 温厚务实，关注人际关系 | 人际困境、伦理选择 |
| **萨特** | 20世纪 | 存在先于本质：自由与责任 | 直面荒诞，强调选择自由 | 意义危机、自由焦虑 |

## 创新 7：情绪感知与干预闭环

### 7.1 核心概念

**不是"分析你的情绪然后告诉你"，而是"感知→判断→干预→平复"的完整闭环。**

PS² 实时分析用户在议会中输入文本的情绪状态，当检测到高焦虑时自动触发呼吸引导——将心理学中的"正念呼吸"技术嵌入 AI 交互流程。

### 7.2 技术架构

```
用户输入文本
      ↓
┌─────────────────────────────┐
│  情绪检测引擎（双层）         │
│                             │
│  Layer 1：本地规则引擎       │
│  lib/emotion-event-signals.ts│
│  ├─ 30+类情绪信号词库        │
│  ├─ 否定检测 (CHAT_MOOD_    │
│  │   NEGATION_LOCAL)        │
│  └─ 规则分层打分             │
│                             │
│  Layer 2：API增强 (可选)     │
│  /api/emotion                │
│  └─ DeepSeek 情绪分类       │
│                             │
│  输出：情绪标签 + 置信度      │
└─────────────────────────────┘
      ↓
┌─────────────────────────────┐
│  阈值判定                    │
│  ├─ 焦虑分 > 0.72?          │
│  ├─ 距离上次触发 > 30秒?     │
│  └─ 用户设置中呼吸引导=开?   │
│         ↓ (全部满足)         │
│  触发呼吸引导弹窗             │
└─────────────────────────────┘
      ↓
┌─────────────────────────────┐
│  呼吸引导动画                │
│  breathing-guide.tsx         │
│  ├─ 吸气 4秒 (放大)          │
│  ├─ 屏息 2秒 (保持)          │
│  ├─ 呼气 4秒 (缩小)          │
│  ├─ 循环 3-5 轮             │
│  └─ 用户可随时关闭            │
└─────────────────────────────┘
```

### 7.3 信号词库设计

`lib/emotion-event-signals.ts` 包含 30+ 类情绪信号，覆盖日常生活各场景：

| 情绪类别 | 示例信号词 | 触发干预 |
|---------|-----------|---------|
| 高焦虑 | 焦虑、不安、紧张、慌、害怕… | ✅ 触发呼吸引导 |
| 低落 | 难过、伤心、哭、绝望、崩溃… | ⚠️ 提示但不强制 |
| 愤怒 | 生气、愤怒、讨厌、烦、恨… | ⚠️ 提示但不强制 |
| 迷茫 | 迷茫、不知道、困惑、迷失… | 不触发（提供导师建议） |
| 平静 | 平静、安心、放松、踏实… | 不触发 |
| 开心 | 开心、高兴、快乐、幸福… | 不触发 |

### 7.4 关键设计决策

| 决策 | 实现 | 理由 |
|------|------|------|
| **否定检测** | `"不焦虑" ≠ "焦虑"` | 防止误触发，提升准确率 |
| **30秒冷却期** | 连续焦虑消息不重复触发 | 防止过度干预，尊重用户 |
| **可调节阈值** | 设置面板中 0.5-0.95 可调 | 不同用户对不同敏感度 |
| **可关闭** | 设置面板中开关 | 用户自主选择 |
| **低性能降级** | 低性能模式跳过模糊/动效 | 保证低端设备可用 |
| **本地优先** | 规则引擎不依赖API | 离线+低延迟 |

### 7.5 用户场景

```
用户在议会中输入：
"我真的好焦虑啊，下周就要答辩了，感觉准备得还不够…"

系统检测到：情绪=焦虑，score=0.85

→ 屏幕渐暗，呼吸引导动画弹出
→ "检测到你正在焦虑。先做一次呼吸调整？"
→ 圆形动画：吸气(放大)…屏息…呼气(缩小)…
→ 3轮后自动结束

→ 用户回到议会，激进派说：
  "焦虑说明你在乎。呼吸完后感觉怎么样？
  我们把'准备不够'拆成具体行动…"

不是"AI分析你的情绪然后说教"，
而是"AI感知焦虑 → 帮你平复 → 然后继续理性讨论"
```

## 创新 8：Server + APK 双模统一工程架构

### 8.1 核心概念

**同一套 Next.js 代码库，同时支持服务器部署和 Android APK 离线导出。**

这不是简单的 WebView 套壳——而是一套精心设计的双模构建系统：Server 模式提供完整在线体验，Export 模式将前端编译为纯静态资源嵌入 APK，通过本地回环代理在离线/弱网环境正常运行。

### 8.2 架构设计

```
             同一代码库: aigc_application_style/
        ┌────────────────┴────────────────┐
        ▼                                 ▼
  ┌──────────────┐                ┌──────────────┐
  │ Server 模式   │                │ Export/APK 模式│
  │ npm run build│                │npm run build │
  │              │                │ :android     │
  ├──────────────┤                ├──────────────┤
  │ 产物: .next/ │                │ 产物: out/   │
  │ Node.js运行时│                │ 纯静态文件    │
  │ API同源调用  │                │ API远程调用   │
  └──────┬───────┘                └──────┬───────┘
         │                               │
         ▼                               ▼
  部署到 Vercel/                 复制到 APK assets/web/
  自有服务器                             │
         │                               ▼
         │                      ┌─────────────────┐
         │                      │  Android WebView │
         │                      │  + AssetLoader   │
         │                      │  + 回环代理37123  │
         │                      └─────────────────┘
         │                               │
         └───────────┬───────────────────┘
                     ▼
              DeepSeek API
         (统一由BFF后端代理)
```

### 8.3 双模式对比

| 维度 | Server 模式 | Export/APK 模式 |
|------|-----------|----------------|
| **构建命令** | `npm run build` | `npm run build:android` |
| **产物** | `.next/` (Node.js运行时) | `out/` (纯静态 HTML/JS/CSS) |
| **API策略** | 同源 `/api/*` | `NEXT_PUBLIC_API_BASE_URL` 远程 |
| **部署方式** | Vercel / 自有服务器 | WebView内置静态资源 |
| **离线能力** | 需要网络 | UI完全离线可用 |
| **LLM调用** | 服务端直连DeepSeek | 通过远程BFF代理 |
| **存储** | localStorage | IndexedDB + localStorage |

### 8.4 WebView 回环代理

APK 在离线状态下，UI 完全可用（静态资源内置）。联网时，API 请求通过以下路径：

```
WebView JS fetch("/api/council/debate")
        │
        ▼
WebViewAssetLoader 拦截
  → 静态资源：加载 assets/web/ 内置文件
  → API请求(/api/*)：不走AssetLoader
        │
        ▼
http://127.0.0.1:37123/api/council/debate
        │
        ▼
ApiLoopbackProxy (Kotlin)
  → 转发到 NEXT_PUBLIC_API_BASE_URL
        │
        ▼
远程 Next.js Server → DeepSeek API
```

### 8.5 为什么这是一个创新

| 传统做法 | PS² 的方案 | 优势 |
|---------|-----------|------|
| 分别开发 Web + App | 一套代码双模式构建 | 降低维护成本50%+ |
| WebView简单套壳 | AssetLoader + 回环代理 | 离线可用 + 联网增强 |
| 前端直连LLM API | BFF统一代理 | API Key零泄露 |
| 单一部署目标 | Server/APK双产物 | 覆盖更多使用场景 |

```
├─ 模糊议题：对未来很迷茫/不知道该怎么办
└─ 边界测试：(空议题)/(纯标点)

验证项：
✅ 路径数量在 [2, 4] 范围内
✅ 每条路径 name 非空且与议题相关
✅ riskScore/benefitScore 在 [0, 100] 范围内
✅ description 不匹配模板套话正则
✅ 无折中/妥协第三条假路径
✅ 同一条议题两次推演，路径结构一致
```

### 辩论系统验证

- 角色一致性：激进派在多轮对话中保持"行动导向"
